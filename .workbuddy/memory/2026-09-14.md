# 第二轮 · 拆词规则精度返工 + 工具自检

## 核心结论：判据错了，不是参数错了
**"token 在语料里出现过"不能用来证明它不是损坏**——损坏本身就是文本，重复出现的损坏（`farmanagement`×4、`waterequirements`×9）会把自己变成"语料词"，从而**自我抑制**。这是原规则 10 个用例漏 5 个的根因。

正确判据 = **形状对（两半都是词）＋ 证据对（两半在语料里真的相邻出现过）**。
只靠形状时，任何足够大的语料都会冒出一堆可拆组合：`Poireaux`→`Poire eaux`（法语"韭葱"）、`Parterres`→`Part terres`（法语"花坛"）、`Contracción`→`Contra acción`、`Disclosure`→`Disc closure`、`Hillside`→`Hills side`、`Converts`→`Conv verts` —— 全是误报。加上"正确写法真的出现过"后，合法词几乎永远不满足。

**结果**：fused_word `594 处/424 词` → **`314 处/158 词`**，西/法误报清零。抽样核对幸存者均为真损坏（`morexpensive`、`specificrop`、`waterequirement`、`agriculturalime`、`improvesoil`；`planutrient` 回原文核对确认正确——"to plan nutrient applications"）。
**代价**：召回换精度。`Puthese`（应为 `Put these`）因左词 `put` 词频不足进不了词库而漏检 → 走 `fix-rules.txt`。这是刻意取舍：该规则驱动**自动改写**，误报=改坏真词。

## 三个自查出来的工具 bug（都不是站点的问题）
1. **`_css_check.py` 行首锚定正则漏读同一行的第二个声明** → 误报 4 个 `--ag-*-border` 未定义。实际 CSS 完好（这些刚好都写在行内第二个位置）。教训：审计脚本自身也要被审计。
2. **测试夹具放进 `SKIP_DIRS` 覆盖的目录**（`audit_scan`、`templates`）→ 目录遍历直接跳过，测试永远"0 命中"，输出"10 missed"看起来像规则全挂，实际根本没跑。**这是最危险的一类 bug：一个永远失败/永远通过的测试比没有测试更糟。** 修法：夹具以**文件路径**作目标（`iter_html` 只对目录遍历套 SKIP_DIRS）＋ 语料只从夹具自身构建（`min_count=1`）→ 自足、可复现、不依赖站点状态；并断言语料非空，避免"空语料=完美通过"。

# 第二轮：结构完整性（div 包裹层）——从 24 error 清到 0

## 先修掉门禁自己的三个盲点（否则看不到真问题）
1. `TAG_RE` 的 `<[^>]*>` 分支会吞掉正文里未转义的 `<`，把 `if (rating < 4)` 变成幻影标签 `<rating>` → 约 1000 条假 unclosed。改为先整块吃掉 `<script>…</script>`／`<style>…</style>`，并去掉 `<[^>]*>`。
2. 结构栈扫描**只能报多余的闭合标签，报不出多余的开标签**（`del stack[i:]` 把未被闭合的开标签一起丢掉了）→ 新增 `unclosed_tag` 规则 + `unclosed` 列表。
3. ⚠️ **第 2 条修完后，`_divfix2.py` 里照抄了同一套"恢复式"栈**，于是 561 个未闭合 div 被它报成"全站 836 文件全干净"。**教训：测量未闭合必须用与顺序无关的计数，不能复用任何带恢复逻辑的栈。**

## 正确判据：`net_div = count(<div>) - count(</div>)`
纯计数、与位置无关，任何嵌套启发式都藏不住缺失的闭合。写脚本/写门禁/做判断都以此为**检测器**；与 `unclosed_tag` 交叉验证，两者独立给出同一个 561。三种取值对应三类状态：
- `net > 0` → 缺 N 个 `</div>` → 修
- `net == 0` → 平衡 → 别碰
- `net < 0` → **多余的 `</div>`**（另一个家族）→ 只报告

## ⚠️ 我犯过的错：把"约定"当成"缺陷"
第一版 `_divfix.py` 用"**widget 处 div 深度是否为 0**"当判据。这**不是缺陷判据，是排版约定**——实测 519 个平衡原文件里，widget 处深度 0 的 77 个、深度 +2 的 12 个，**两种都合法**。于是它在 12 个本来就干净的文件上多插了 2 个 `</div>`，把 `<main>` 吞掉（`div 50/52`）。
**正确判据是"文件结束时还开着"（net 计数），与"在 widget 前面还是后面闭合"无关。**

## 插入点（量出来的，不是猜的）
- 全部 519 个平衡原文件里 **`depth@<footer>` = 0 占 100%**（页面包裹层从不包住 footer）。
- 有 widget 的文件：77 个在 widget **之前**闭合包裹层，12 个在其后 → 取"之前"。
- 插入点优先级：`<div class="rating-feedback-widget"` → `<footer` → `</footer>` → `</body>`，**逐个试、试到通过校验为止**。

## 每次改写都必须自证（本轮最关键的工程约束）
插入 N 个 `</div>` 到位置 P，只有满足下面 3 条才允许落盘：
1. **`depth@P >= N`** ← 最关键。若该处只开着 m < N 个 div，插进去就是把深度推到负数，**等于亲手制造"多余闭合"这个更糟的缺陷**。这条正是区分"补页面包裹层"和"补 footer 内层"的唯一依据。
2. 改写后**深度处处不为负**。
3. `net_div == 0` 且 `</footer>` 仍是顶层（其后深度 0）。
不通过的文件**一律不写**、列出来交人工。`_divfix3.py`（修 313 个 + 回滚 12 个）/ `_surplusfix.py`（删多余闭合）/ `_verify_div.py`（独立验收，836 文件全过）留在 `audit_scan/`。
